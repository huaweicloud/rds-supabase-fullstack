# 运行环境与验证矩阵

版本0.3.7a1。业务逻辑共用，安装材料按平台交付。选择目标平台不等于已通过该平台验收。

| 环境 | 定位 | 当前证据 | 尚需验证 |
|---|---|---|---|
| Windows x64 / CPython3.12 64位 | 首个客户交付目标，开发联调包 | 目标wheel元数据检查、安装前架构及文件校验代码 | Windows原机安装/运行/权限/网络，当前不能称正式支持已验收 |
| Windows ARM64或32位 | 当前包不适用 | 安装前拒绝 | 专属依赖和安装验收，不能强装x64包 |
| 其他Python版本 | 不在当前Windows包范围 | 项目语言最低版本不等于此包支持版本 | 单独依赖解析与测试 |
| macOS开发机 | 开发回归环境 | 本地测试、stdio和产品wheel验证 | 不替代Windows验收 |
| Linux/其他macOS环境 | 可移植目标，未交付平台包 | 无该平台发行证据 | 需求确认、打包与实机验收 |
| 码道客户端 | 最后联合验收 | 通用MCP配置模板 | 具体版本的加载、确认、Skill和端到端验收 |

## Windows首次使用顺序

1. 解压至新目录；保留ZIP的SHA256外部校验值。包内清单用于检测损坏，不是数字签名或发布者身份认证。
2. PowerShell运行 `py -3.12 .\scripts\verify_delivery.py`，默认检查脚本所属包目录。此步骤不安装、不联网、不读取凭据。输出系统、架构、Python与校验结果。
3. 运行 `& .\scripts\install-development.ps1`。它在安装前重复校验，再创建包内独立.venv。错误立即停止，不覆盖旧环境，不全局修改Python。
4. 运行 `& .\.venv\Scripts\python.exe -m mcp_server_supabase.diagnostics offline`。这是本地协议验证，不是云接口验收。
5. 在可信本机配置中设置接口身份后，可先运行diagnostics check（不联网），经授权再运行readonly --allow-cloud-read。

环境配置、MCP宿主兼容、云服务网络/身份是三个独立检查层。配置完整不证明云网络可达；浏览器登录不证明MCP可鉴权。创建/修改等业务规则不按操作系统分叉。

## Windows原机验收执行单

| 用例 | 必须观察的结果 |
|---|---|
| 空格和中文解压路径 | 安装、子进程stdio、工具发现正常 |
| Python3.11、32位或ARM64 | 安装前明确拒绝，不创建环境 |
| 缺失/修改文件、多余wheel | 校验失败，不继续安装 |
| 已有.venv | 不覆盖，提示新目录安装 |
| 依赖安装 | 无网络离线安装、pip check、本版本完整单元测试；结果单独记录 |
| 权限与状态目录 | Windows ACL仅允许适当用户访问；Unix chmod不能替代ACL |
| 重启与账本 | 未决操作保留，不能删除或更换账本绕过防重复 |
| 客户端配置 | 使用.venv\Scripts\python.exe绝对路径，配置中的反斜杠按JSON转义 |
| 云端异常 | 权限/连通/契约问题明确区分，不泄露Token或原始响应 |

当前依赖安全策略冲突仍在，安装成功不等于生产批准。客户是否自带Python或需要捆绑运行时属于发布方案决策；当前包要求用户安装Python3.12，没有提供内嵌运行时。更新包解压新目录，真实使用的SUPABASE_STATE_FILE保持原路径并备份，不能直接切到新空账本重放未知操作。
